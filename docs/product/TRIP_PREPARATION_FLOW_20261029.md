# 여행 준비와 차량 관측의 연결

기준: 2026-10-29. 로컬 후속 구현이며 독립 검수 전 원격 main에 반영하지 않는다. 실제 고객 연구·사용률·유지율·매출을 측정한 자료가 아니다.

## 기존 기능 재사용

저장된 여행의 장소·입퇴실 날짜를 기존 식사 선택과 같은 여행 key로 연결한다. 바비큐 사진·구성과 선택 저장소는 복제하지 않는다. 차박의 기존 장면과 차량 제어도 재구현하지 않는다. 준비 단계 선택·체크·다음 여행 가져오기는 차량 setter, 안내 시작, 음성 기능을 호출하지 않는다.

## 도착–체류–철수

내 캠핑의 준비 카드에 `도착했을 때 / 머무는 동안 / 돌아가기 전`을 둔다. 사용자가 단계를 선택하고 직접 살펴본 항목을 체크한다. 차박 화면의 준비 이어가기 버튼은 같은 저장 여행으로 돌아온다. 위치 도착이나 UX 제한 해제를 준비 완료·주차 신호로 사용하지 않는다.

- 도착: 주변·이용 수칙, 전원 계획, 인원에 맞는 준비물.
- 체류: 실내·주변 환경, 전원 계획, 식사 구성과 보관.
- 철수: 케이블·짐, 문·창문 직접 둘러보기, 두고 가는 물건·쓰레기.

이는 사용자의 준비 기록이며 출발 안전 판정이 아니다. 문·창문의 raw 0, 부분 영역·빈 목록·stale 값으로 닫힘을 추정하거나 체크하지 않는다. 신뢰할 수 있는 PARKED 공급 계약이 없으므로 기존 물리 제어 차단을 유지한다.

## 실제 관측이 바꾸는 준비

SDK의 원본 SOC 값·단조 표본 시각·owner·native epoch를 한 immutable sample로 보존한다. `vehicle()` 조회 시각으로 표본을 새로 만들지 않는다. 현재 binding에서 온 0–100의 유효한 값이며 60초 이내인 경우에만 배터리를 준비 안내에 사용한다.

신선한 SOC가 30% 미만이면 충전 계획 확인을 먼저 배치한다. 그 외에는 체류 중 전원 사용 계획을 안내한다. 30%는 준비 검토를 위한 제품 휴리스틱이며 체류 가능 시간·귀환 가능성·안전 기준을 뜻하지 않는다. 결측·오래된 값·단절에서는 차량에서 직접 배터리를 살펴보는 과업으로 돌아간다. SDK 관측이 수동 체크를 생성하지 않는다.

owner/epoch·host session·조언 범주가 바뀌면 관련 전원 체크를 다시 하도록 기존 acknowledgement를 철회한다. 같은 조건의 반복 polling은 체크를 지우거나 사용 집계를 늘리지 않는다. STOP 때 캐시된 Vehicle을 disconnected로 만들고 host revision도 바꾸므로 화면이 중간 단절 상태를 그리지 못한 경우에도 옛 전원 체크가 재사용되지 않는다.

## 저장과 다음 여행

수동 체크·선택한 준비물·단계는 앱 전용 로컬 저장소에 여행별로 보관한다. revision 비교 후에만 비동기 reconcile을 저장하므로, 늦은 화면 효과가 새 체크·단계 변경·가져오기를 덮어쓸 수 없다.

다음 여행 목록 보관은 사용자가 선택한 물품과 기존 식사 선택만 저장한다. 다른 여행에서 명시적으로 가져올 때 ARRIVAL·빈 체크로 시작하며 이전 관측·완료·확인 시각을 이월하지 않는다. 인원이 바뀌면 식사·짐 구성을 다시 살펴보도록 안내한다. 새 주문·예약·결제를 만들지 않는다.

## 동의와 로컬 집계

준비 과정의 횟수 집계는 기본 꺼짐이다. 사용자가 켠 뒤 발생한 직접 체크·단계 변경·가져오기만 세며 소급 집계하지 않는다. 끄면 해당 집계를 비운다. 이 집계에는 장소 ID·좌표·원시 차량값·사용자 식별자·날짜·자유 텍스트가 없고, 기존 Telemetry/PostHog/Sentry 경로에도 연결하지 않는다.

횟수는 기능 사용의 로컬 기록이며 효용 개선·고유 사용자·MAU·유지율의 증거가 아니다. 비교 과업 시간·화면 이동·오해 감소와 고객·파트너 검증은 기존 [검증·사업 계획](VALIDATION_AND_BUSINESS_PLAN.md)의 미실행 계획으로 남는다. 모집·외부 접촉·추가 결제·새 권한 요청은 수행하지 않는다.

## 검증 범위

현재 소스 60개의 해시와 PleosDebug 빌드, 앱 테스트 283개(실패·오류·건너뜀 0)를 연결했다. 원본 관측 시각, stale·단절·다른 owner/epoch·host 재개, raw 0·부분 영역, 체크 철회와 반복 poll, 여행 key 격리, 가져오기 초기화, 늦은 reconcile/ABA, opt-in 경계의 반례를 포함한다. 모의 회귀를 실제 차량 동작으로 표시하지 않는다.

새 PleosDebug APK의 설치 해시가 빌드 파일과 일치함을 확인했다. 부분 AVD 실행에서 원본 SOC 표본 시각·세대와 요청 귀속 로그, ARRIVAL/STAY 단계의 저장을 확인했지만, 전체 단계·동일 ViewModel 재개·다음 여행 가져오기의 화면 수용 검증은 아직 미완료다. 현재 공식 AVD가 Awake/Display ON인 상태에서도 검은 화면·null UI root를 반환하며 시스템 drivingview의 ANR/네이티브 충돌이 기록됐다. 정상 앱 재시작과 wakeup으로 복구되지 않았다. 추가 AVD 재시작은 기존 두 회 한도 초과 및 현재 상태 보존 위험으로 자동 승인 검토가 실행 전에 거부했으며 재시도하지 않았다. 원인은 앱 단독 결함으로 확정하지 않는다. 이전 APK나 모의 테스트를 최신 전체 실기 통과로 대신하지 않는다. 상세 기록은 로컬 `review-runtime/trip-context-20261029/CURRENT_AUDIT.json`과 별도 최종 검수 패키지에 보존한다.

## 내비 진단과 남은 범위

기존 두 캡처의 같은 POI·유효 좌표는 50–100m 차이로 20m 일치 기준에 거절됐다. callback 도착은 3.233초·2.164초였으므로 이 두 거절은 timeout이 아니다. 앱의 외부 고캠핑 ID와 SDK 지도 POI ID를 같은 namespace로 쓰는 경계는 확인했지만 실제 변위의 원인은 아직 입증하지 못했다. 경로 진입점·지도 좌표 보정·원본 정밀도는 가설이며 기준을 완화하지 않는다. 안내 시작은 실행하지 않는다.

새 debug trace는 비영속 process·owner·session·request·sequence를 구분한다. 원본 request가 없는 SDK callback과 Assist 기록은 connection/process 수준의 귀속 한계를 명시한다. SmartGlass 60001·목표 온도 오류·초기 SOC capability timeout을 숨기거나 전체 SDK 성공으로 바꾸지 않는다.
