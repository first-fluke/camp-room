# Camp Room 제품 요구사항 정의서

- 버전: 1.2 · 2026-10-25
- 제품명: Camp Room / 캠프룸
- 제품 형태: Pleos 차량용 독립 캠핑 앱
- 기준 자료: 기존 공모전 신청서, 사용자 제공 `docs/product/pleos-sdk.spec.jsonl`, SDK 검토 `docs/product/PLEOS_SDK_REVIEW.md`
- 구현 기준: 본 PRD와 `FUNCTIONAL_SPEC.md`, `plans/contracts/camp-room-api.md`

## 1. 제품 목표

캠프룸은 캠핑장을 찾는 순간부터 차량으로 이동하고 현장에서 생활한 뒤 귀가하는 과정을 하나의 여행으로 연결한다. 예약 가능 여부, 날씨, 차량 배터리와 실내 상태를 따로 확인하는 부담을 줄이고 앞좌석 독서와 뒷좌석 휴식처럼 동승자의 다른 활동을 구역별 차박 설정으로 지원한다. 준비물이 부족할 때는 캠핑 조건에 맞는 상품을 장바구니에 담고 자택 또는 수령 가능한 캠핑장으로 주문한다.

캠프룸은 일정·장소·저장한 공간 설정·구매 준비를 다음 캠핑에도 재사용하는 독립 앱이다. Kotlin·Jetpack Compose 화면이 FastAPI 서버와 연결된다. `pleos` 실행 환경은 Vehicle, NaviHelper, FusedLocation, TextToSpeech, SpeechToText를 차량 안에서 직접 호출한다. `demo`는 같은 Android 화면에서 차량·내비 시뮬레이터와 기기의 위치·음성 서비스를 사용한다. 예약·주문 시연의 실제 외부 승인 여부는 별도로 표시한다.

## 2. 핵심 사용자와 문제

| 사용자 | 완료하려는 일 | 현재의 불편 | 제공 가치 |
|---|---|---|---|
| 첫 전기차 차박을 준비하는 민서 | 날짜·시설·차박 허용 조건에 맞는 장소 선택 | 예약·날씨·배터리를 여러 화면에서 비교 | 선택한 장소와 일정이 이동 및 현장 화면에 계속 유지 |
| 가족과 자주 캠핑하는 도윤 | 앞좌석 독서·뒷좌석 휴식 환경 구성 | 구역별 설정을 매번 다시 조작 | 저장 장면 적용, 항목별 결과와 현재 상태 확인 |
| 준비물을 놓친 동행자 | 필요한 물품을 체류 일정에 맞게 받기 | 캠핑장 수령 가능 여부와 배송일 불확실 | 수령 조건·도착 예정일 검증 후 주문 |

## 3. 주요 정보 구조

세 주 메뉴는 **찾기 / 내 캠핑 / 차박**이다. 준비물은 공통 상단의 장바구니와 내 캠핑의 준비물 제안에서 접근한다. 차량용 Android 가로 화면에서는 네이티브 NavigationRail과 넓은 콘텐츠 영역을 사용하고 작은 화면에서는 하단 탐색으로 전환한다. 날짜·인원·현재 여행 정보는 화면 간 공유하며 메뉴를 바꾸거나 새로 고침해도 유지한다.

| 메뉴 | 주요 내용 | 완료 조건 |
|---|---|---|
| 찾기 | 지역·날짜·인원·차박·시설 필터, 장소 목록, 상세, 가용성 | 조건에 맞는 장소를 내 캠핑에 저장 |
| 내 캠핑 | 숙박 일정, 날씨, 규칙, 경로·배터리, 준비물·배송 | 이동 계획 확인과 시연 길안내 시작, 준비물 주문 |
| 차박 | 현재 차량 상태, 공간 배치, 장면, 구역별 제어, 출발 점검 | 장면의 항목별 처리 결과와 관측 상태 확인 |

## 4. 이번 제공 범위

### 4.1 캠핑장 탐색

지역, 숙박 날짜, 인원, 차박 허용, 샤워실·전기·반려견 동반 등의 시설 조건으로 검색한다. 시설 데이터와 예약 데이터는 출처가 다를 수 있으므로 각각 출처·확인 시각을 유지한다. 캠핑용 전기 제공과 전기차 충전 허용 여부를 별도로 표시한다. 장소 상세에는 입퇴실 시간, 매너타임, 차량 진입·차박 조건, 수령 조건, 운영 규칙을 제공한다.

전체 숙박 기간에 대한 예약 정보는 `available / limited / unavailable / unknown` 상태로 구분한다. 공급자가 제공한 잔여 자리만 표시하고 공급자가 실제 예약 수와 판매 가능 수를 제공하지 않으면 예약 건수·예약률을 만들지 않는다. 조회 시각이 지난 상태는 갱신을 요구한다. Android demo flavor 시연의 모든 장소·가용성 데이터는 데모임을 공통 배지와 공급자 이름에 명시한다.

### 4.2 여행과 이동

현재 여행에는 장소, 체크인·체크아웃, 인원과 길안내 시작 상태를 저장한다. 예약 참조와 여러 목적지의 여행 편집은 후속 확장 범위다. 날씨는 캠핑장 좌표 및 체류 일정 기준의 예보이며 실내 온도 센서와 구분한다. 현재 배터리, 예상 거리·시간·에너지, 예상 도착 잔량과 충전 경유 정보를 함께 보여준다. demo flavor의 길안내는 데모 경로 의도를 만든 것으로 표시하고 실제 내비 실행으로 표현하지 않는다. `pleos`는 NaviHelper에 목적지를 전달하고 실제 길안내 상태 이벤트를 확인한다. 경유지 계약은 SDK 적용표에 기록한다.

### 4.3 차박 공간

기본 장면은 짐 정리, 함께 쉬기, 앞좌석 독서·뒷좌석 휴식, 취침 준비, 출발 준비다. 앞뒤 공간의 조명·차광·좌석 편의와 차량이 지원하는 공조를 조합한다. 사용자가 명시적으로 적용할 때만 명령을 실행한다. 현재 값 확인 → 지원 범위 확인 → 명령 → 항목별 결과 → 지원되는 관측값 재확인을 수행한다.

명령 수락은 물리적 완료와 다르다. SDK에 대응 getter나 listener가 있는 항목만 관측 상태로 확인한다. 콜백이나 getter가 없는 항목은 확인되지 않은 상태를 유지한다. 부분 실패는 성공 항목을 숨기지 않고 실패 항목과 재시도 대상을 보여준다. 충전 목표 잔량의 getter 부재, 좌석 메모리 성공 콜백 부재 등은 SDK 검토서와 동일하게 반영한다.

사용자가 제공한 SDK에는 현재 도로 속도나 기어 P를 확정하는 필드가 없다. `motionState`는 플랫폼 호스트가 주입하는 별도 계약이며 알 수 없음은 정차로 취급하지 않는다. 시연은 모의 정차 상태임을 표시한다. 좌석 자동 펼침 등 안전 확인이 필요한 동작은 확인된 플랫폼 계약 전에는 네이티브에서 실행하지 않는다.

### 4.4 준비물과 캠핑 커머스

침낭, 휴대용 조명, 수납·식사 물품 등의 상품마다 추천 이유를 표시한다. 현재 상품 카탈로그와 추천 이유는 데모 데이터이며 시설·날씨·여행 조건을 계산하는 추천 엔진은 후속 확장 범위다. 추천 상품에는 재고·가격·수량이 있다. 장바구니 수량 변경과 삭제, 배송 견적, 데모 주문 생성을 끝까지 처리한다.

배송지는 자택과 캠핑장 중 선택한다. 캠핑장 배송은 장소의 수령 허용 여부, 수령 위치, 이름 표기·운영 시간 등 조건, 예정 도착일과 체류 기간을 검증한다. 수령이 불가하거나 일정이 맞지 않으면 주문을 막고 자택 배송 등의 수정 가능한 선택을 보여준다. 최종 금액과 배송지를 확인한 후 결제를 명시적으로 실행한다. 결제는 실제 승인이 아닌 **데모 주문**이다. 중복 클릭 및 재요청은 같은 idempotency key에 같은 주문을 반환한다.

## 5. 대표 사용자 여정

1. 사용자가 찾기에서 강원·2명·차박·샤워실을 선택하고 날짜를 정한다.
2. 캠핑장 상세에서 차박 규칙, 가용성 출처와 조회 시각, 전기·충전 차이를 확인한다.
3. 내 캠핑에 저장하고 예보와 SOC 기반 경로 미리보기를 확인한다.
4. 길안내 시작을 눌러 데모 내비 상태가 바뀌는 것을 확인한다.
5. 차박에서 앞좌석 독서·뒷좌석 휴식을 적용한다. 구역별 조명과 차광 결과 및 관측 상태를 확인한다.
6. 준비물 추천에서 상품을 담고 캠핑장 수령 조건과 배송 예정일을 확인한다.
7. 데모 결제를 실행한다. 주문번호·금액·배송지·도착 예정일이 저장되며 실제 결제로 오인하지 않는다.
8. 출발 준비에서 문·창문·배터리·다음 목적지를 확인한다.

## 6. 품질과 완료 기준

| ID | 요구사항 | 검증 |
|---|---|---|
| P1 | 세 메뉴가 하나의 여행을 공유하고 새로 고침 후 유지 | Android emulator 실제 조작 및 서버 저장 조회 |
| P2 | 검색·상세·가용성·저장이 연결 | 필터 결과와 저장된 장소 검증 |
| P3 | 날짜 오류와 공급자 미지원 상태를 정직하게 표시 | API 오류 및 unknown 상태 검증 |
| P4 | 예보·차량 측정값·예상 도착 잔량의 의미를 구분 | UI와 API 응답 확인 |
| P5 | 장면 적용에 명령 결과와 readback을 구분 | 부분 실패·미지원 테스트 |
| P6 | 장바구니부터 데모 주문까지 동작 | 금액·재고·배송·중복 제출 검증 |
| P7 | 키보드·터치·가로/작은 화면에 사용 가능 | label·focus·대비·반응형 확인 |
| P8 | 동작하는 앱을 실제 Android emulator에서 녹화 | 입력과 결과가 포함된 MP4 |

오류·로딩·빈 결과 상태가 사용자에게 보이고 재시도 가능해야 한다. 앱과 관리자 화면은 한국어·영어를 지원하며 앱에서 시스템 언어 따르기를 선택할 수 있다. 날짜·금액과 STT/TTS 언어는 선택한 언어를 반영한다. 공급자 원문과 일부 SDK 진단 문구는 원래 언어로 남을 수 있다. 초기 데이터는 명확한 데모이며 비밀키를 클라이언트에 넣지 않는다. 임의의 사용자 입력을 코드나 SQL에 삽입하지 않는다. 기록하는 데이터는 시연에 필요한 여행·장바구니·주문 정도로 제한한다.

## 7. 구현 구조와 범위 구분

| 구성 | 구현 책임 |
| --- | --- |
| `apps/pleos` | Kotlin·Compose, Hilt, ViewModel/StateFlow, 생성된 Ktor 클라이언트, 5개 Pleos SDK |
| `apps/api` | Python 3.14·FastAPI, 명시적 DTO·OpenAPI, 공급자 어댑터, 여행·커머스 처리 |
| `apps/admin` | Next.js 운영 화면·서버 BFF, 관리자 세션과 관리 API 연결 |
| `apps/worker` | 인증된 관리 API로 캠핑장·날씨 캐시 갱신, 제한된 재시도 |
| Turso / SQLite | 같은 32개 STRICT 테이블, 3NF 관계, 주문 트랜잭션과 캐시·작업 이력 |

API 모델에서 내보낸 `apps/api/openapi.json`으로 `jvm-ktor` 클라이언트를 생성한다. 앱의 요청·응답 타입과 서버 계약을 함께 검증하며 생성 파일을 직접 수정하지 않는다. 서버의 차량 상태 테이블은 명시적인 데모 시뮬레이터용이고 실제 차량 상태는 로컬 SDK에서 읽는다.

시연은 앱 실행과 조작, API·저장소의 상태 변화, 입력·배송 검증과 데모 주문을 확인한다. 실제 예약 재고, 결제 승인과 택배 접수에는 각 사업자의 연동이 추가로 필요하다. 원격 Turso 검증, APK 빌드, 에뮬레이터 동작과 실차 검증은 수행한 범위를 각각 기록한다. 구조는 [서버 구조도](architecture/SERVER_ARCHITECTURE.md), 데이터 관계는 [ERD](database/ERD.md)를 따른다.

## 8. 측정 계획

제품 검증 지표는 장소 저장·길안내·장면 적용·출발 준비를 도움 없이 완료하는 비율 90%, 다음 캠핑 시 재사용률 40%를 초기 가설로 둔다. 이는 출시 성과가 아니다. 이번 구현의 성공은 핵심 여정이 서버 상태와 함께 끝까지 이어지고 실패 및 정보 미제공 상태를 잘 설명하며 실제 녹화로 확인할 수 있는지로 판단한다.

## 9. 외부 데이터와 운영

GoCamping과 KMA는 서버의 HTTP 어댑터로 연결한다. 발급된 키는 루트 `.env` 또는 서버 환경변수에서 읽는다. `demo`, `auto`, `live` 모드를 구분하고 데이터마다 출처·갱신 시각·누락 상태를 유지한다. 현재 외부 공급자 키는 미설정이며 계정 가입과 키 발급은 기존 로컬 Aside MCP 세션에서 진행할 작업이다.

관리자는 공급자와 DB 상태를 확인하고 캠핑장의 택배 수령 조건과 데모 주문 처리 상태·메모를 수정한다. 워커는 현재 여행과 최대 두 곳의 대안 캠핑장 날씨를 갱신한다. 공급자 장애가 생겨도 마지막 성공 캐시와 작업 이력은 보존하며 오래된 정보를 새 예보처럼 표시하지 않는다.

## 10. 후속 서비스 확장

국가·지역별 디렉터리, 예약·날씨 공급자를 어댑터로 추가한다. 예약 가능 정보는 날짜·인원·사이트 조건에 맞는 응답만 사용하며 실제 예약 건수나 예약률은 공급자가 그 수치와 모집단을 제공할 때 표시한다.

캠핑 커머스는 판매처별 카탈로그·재고·가격·배송 견적·주문 연동으로 확장한다. 사용자는 준비물을 앱에서 담고 구매한 뒤 자택 또는 캠핑장으로 받는다. 캠핑장 배송에서는 수령 정책, 수령자·사이트 표기와 체류 기간 안의 도착 예정일을 확인한다. 현재 데모의 주문·수령 검증 흐름을 실제 판매처 계약으로 이어가는 단계이며 결제·배송 연동 완료를 전제하지 않는다.

다중 여행, 예약 참조, 동행자별 공간 설정과 조건별 상품 추천도 확장 대상이다. 현재 단일 데모 프로필을 일반 사용자 서비스로 운영하려면 사용자 인증·권한과 프로필 연결을 먼저 구현해야 한다.
