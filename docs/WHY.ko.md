# 설계 선택

## 차량 앱은 Kotlin과 Compose

캠프룸의 화면은 Pleos 차량 안에서 실행한다. Kotlin·Jetpack Compose를 사용하면 차량 SDK, 화면 수명주기, 권한 요청과 상태 표시를 한 앱에서 관리할 수 있다. `demo`와 `pleos` 실행 환경이 화면과 도메인 모델을 공유하며 플랫폼 연결만 바꾼다.

Vehicle, NaviHelper, FusedLocation, TextToSpeech, SpeechToText는 각각 차량 상태·제어, 이동, 위치, 음성 출력, 음성 입력을 맡는다. Hilt가 실행 환경에 맞는 연결을 주입한다. 차량의 현재 상태와 서버의 데모 상태는 같은 값으로 간주하지 않는다.

## API 계약에서 Kotlin 클라이언트 생성

서버가 필드를 바꾸면 앱의 DTO와 요청 코드도 함께 확인해야 한다. FastAPI 모델에서 OpenAPI를 내보내고 `jvm-ktor` 클라이언트를 생성해 이 계약을 코드로 공유한다. 생성된 파일의 수정은 생성 설정과 서버 모델에서 처리한다.

앱 저장소는 생성된 응답을 화면용 모델로 변환한다. 이 경계 덕분에 Compose 화면이 공급자의 필드나 HTTP 구현을 직접 다루지 않는다. 실제 직렬화는 Ktor MockEngine 테스트로 검증한다.

## 공급자 어댑터와 갱신 워커

국내 캠핑장 정보와 날씨는 서로 다른 서비스에서 온다. 어댑터가 각 응답을 앱의 모델로 변환하고 출처·조회 시각·누락 값을 남긴다. 예약 재고를 제공하지 않는 디렉터리 API에서 예약 수를 추정하지 않는다.

워커는 관리 API에 갱신을 요청하고 API가 캐시·임대·실행 이력을 관리한다. 앱 요청마다 같은 외부 데이터를 반복해서 가져오는 일을 줄이면서 API와 워커가 서로 다른 갱신 규칙을 갖지 않도록 했다.

## Turso와 3NF

캠핑장 시설, 장바구니 항목, 주문 항목과 예보는 각각 여러 행으로 저장한다. 32개 STRICT 테이블의 기본 키·외래 키·제약조건으로 데이터 관계를 명시한다. API용 응답 모양을 하나의 JSON 문서로 저장하지 않는다.

주문은 재고 차감과 기록 저장을 함께 커밋한다. 주문 당시 상품명·가격·배송지는 이력으로 남기고 현재 상품 정보와 구분한다. 합계는 항목과 배송료에서 계산한다. 구조와 검토 근거는 [ERD](database/ERD.md)와 [독립 DB 검토](database/SCHEMA_REVIEW.md)를 참고한다.

## 운영 화면을 별도로 둔 이유

공급자 장애 확인, 택배 수령 조건 수정과 주문 메모는 운영자가 처리할 일이다. Next.js 관리자 화면에서 이 작업을 제공하고 차량 앱에는 캠핑에 필요한 흐름을 유지한다. 관리자 인증과 공급자·DB 비밀값은 서버가 관리한다.
